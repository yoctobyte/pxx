# PXX 0.1.0-beta.1 — codename "Blaise"

## Start here

**PXX** is one compiler, written from scratch, for Pascal (the Free Pascal
dialect), C, and Nil Python (a Python-shaped language compiled ahead of time).
It turns a source file into a finished static Linux program, cross-compiles
for i386, aarch64, arm32, riscv32 and wasm32, builds firmware for the ESP32-S3
and ESP32-C3, and compiles itself.

**Try it** on x86-64 Linux. Download `pxx-v0.1.0-beta.1.tar.gz` and
`SHA256SUMS` from **[download location: to be filled in on release day]**,
then:

```sh
sha256sum -c SHA256SUMS
tar xzf pxx-v0.1.0-beta.1.tar.gz
cd pxx-v0.1.0-beta.1
./install.sh --yes
```

Save this as `hello.pas`:

```pascal
program hello;
begin
  writeln('Hello from PXX');
end.
```

```sh
./pxx hello.pas hello
./hello
```

```text
ok: hello  [code=600B  data=416B  bss=34600B  procs=37  codeseg=3808B]
Hello from PXX
```

The figures on the `ok:` line vary between builds. The same `./pxx` compiles
C (`./pxx hello.c hello`) and Nil Python (`./pxx hello.py hello`).

**What works:** Pascal and C are solid, and real C programs such as SQLite,
Lua and QuickJS compile unmodified and give their expected output. Nil Python
is best effort. On an ESP32, Pascal, C and Nil Python programs run on real
boards. The details are under Frontends, Targets and Demos below. To try the
ESP32, with or without a board, start at `docs/getting-started/esp32.md` (on
the website: Getting started, Getting started on the ESP32). It needs
ESP-IDF v6.0.1, a separate install of several gigabytes.

**What does not:** read `docs/reference/known-issues.md` (on the website:
Reference, Known issues) before you rely on a result. It lists every open
problem, starting with programs that compile and silently give a wrong answer.

**Found a bug?** `docs/reference/reporting-bugs.md` (Reference, Reporting
bugs) says what to include and how to cut a program down to a small one.

One compiler for **Pascal, C and Nil Python** (a Python-shaped language),
written from scratch, that compiles itself and produces finished static
programs for Linux and the ESP32.

**The flagship: Pascal and Python on an ESP32, measured on the chip.**
- On a physical ESP32-C3 and ESP32-S3 (2026-09-28, with a build made after v446, `cdd6fd3c1f`), every
  example passed: 12 plus a new Wi-Fi access point on the C3, and 16 on the
  S3 with the socket-error test and settings kept across a hardware reset.
  Pin v441 passed the same sets the day before (C3 12 of 12, S3 18 of 18).
- One program can mix languages. Python importing a Pascal unit, and Pascal
  calling C, both ran on a real C3 (the same build).
- Over real Wi-Fi (the same build): 300 HTTP fetches on the S3 and 300
  MQTT sessions on each chip, 0 errors. Two minutes after the last round,
  free heap was higher than at the start on both chips.
  Deliberate-leak controls lost 1,116 to 1,438 bytes per round, so a leak
  would have shown.

**Memory leaks were treated as release blockers.**
- Before v441: 164 automated leak checks, 49 Pascal shapes on seven targets
  at `-O0` to `-O3`, threaded programs on four targets, and real programs.
  Five compiler leaks were found and fixed in v441. Only the Nil Python
  checks ran beside a deliberate leak then. The Pascal checks got one after
  v448: 4 blocks live, and 1,080 with the planted leak, on x86-64 (5 and
  1,186 on i386 and arm32). The C checks still have none.
- Found and fixed since: `clear()` on a list or dict (v442), a dropped Nil
  Python container held until the function returned (v446), the same for a
  comprehension (v447), `str(i) * n` (v446), and per-loop temporaries on
  wasm32 (v447).
- Found and fixed in v449: a handled exception's destructor never ran, and
  `del name` freed nothing until the function returned (see "Memory leaks"
  below). Still open: reference cycles are never freed; there is no cycle
  collector, by design.

**Cross-platform.** x86-64 Linux is the host. i386, aarch64, arm32 and
riscv32 Linux run under QEMU, and wasm32 under wasmtime. The compiler
rebuilds itself on i386, aarch64 and arm32 (tree `0381cb6e4d`). Threads,
`threadvar` and C `__thread` give each thread its own copy on x86-64, i386,
aarch64 and arm32 (v446). Values that were right only on x86-64 were found by
comparing against GCC and FPC on every target: five in C (fixed in v446) and
six in Pascal (fixed in v447).

**C.** c-testsuite 220 of 220 on x86-64 (v441, again with v445), and 219 of
220 on the ESP32-S3 and C3 under QEMU (v441). SQLite, Lua, zlib, cJSON,
Duktape, QuickJS, the Tiny C Compiler and BusyBox build unmodified and match
GCC's build of the same source or their recorded output (v441). BusyBox builds to a 171,224-byte static program with no
libc (v441).

**Known issues, the headlines** (full list in
`docs/reference/known-issues.md`):
- Nil Python is best effort. It is not CPython, and exact CPython behaviour
  is not a goal of this beta.
- C `long double` is 8 bytes, not GCC's 16.
- ESP bare-metal images run under QEMU only; on a chip, use the ESP-IDF
  profile.
- The OpenSSL backend for `https://` runs on x86-64, and on i386 from v448
  (`docs/library/networking.md`).
- `-O3` is experimental, wasm32 is the least tested target, and riscv32
  Linux has no threads (`--threadsafe` is refused there). There is no
  Windows, macOS or BSD target.
- Active development is paused after this beta. We are looking for sponsors.

PXX is a self-hosting compiler for the Pascal dialect of Free Pascal, written
from scratch. It has its own runtime library, its own ELF writer and its own
linker, so a compiled program is a finished static executable that needs no
`as`, `ld` or libc. The same backend also compiles **C** and **Nil Python**, a
Python-shaped language. This is the first beta: `0.x` means the language, the
ABI and the command line may still change between releases.

This release is **pin v441**.

**Active development is paused after this beta. We are looking for sponsors
to continue it.** What continued development would bring: memory-leak
hardening across every target, Nil Python maturity, and more platforms. If you
or your organisation would fund that, open an issue at
<https://github.com/yoctobyte/pxx/issues> titled "Sponsorship".

## Frontends

| Language | State in this release |
| --- | --- |
| **Pascal** | Solid. FPC's `objfpc` and Delphi modes: classes, interfaces, generics, managed strings, dynamic arrays, exceptions and threads. The compiler compiles itself to a byte-identical binary. FPC's own test suite: **427 pass, 0 fail**, 73 skipped and 50 auto-gated, out of 550 tests. |
| **C** | Solid. A C99-class dialect with common GNU extensions and PXX's own C runtime. **c-testsuite: 220 of 220** single-program tests pass on x86-64. The same 220, compiled for the ESP32-S3 and run under Espressif's QEMU with v441: 219 pass, 0 fail, 1 skip, as with v425; for the ESP32-C3, also 219/0/1 with v441 (`00187.c` needs a writable file system the test image does not mount). Real C programs, below, are checked against GCC's build of the same source. |
| **Nil Python** | **Best effort: the least mature frontend, with a real backlog.** CPython compatibility is not a goal of this beta. It compiles Python-shaped source ahead of time to a static binary. It is not CPython and does not run CPython's standard library: imports resolve to PXX's own implementations first, and several of those cover only part of the module they are named after. If a program depends on exact CPython behaviour, check it. |

A small BASIC frontend also exists. The Rust and Zig frontends are
experimental proofs of concept; do not build on them.

## Targets

- **x86-64 Linux** is the host and the only native target. The compiler
  self-hosts there, and it is the most heavily tested target.
- **i386, aarch64, arm32 and riscv32 Linux** are cross targets, run under
  **QEMU 10.2.1** in user mode. A one-line program in Pascal, C and Nil
  Python compiles and runs on each of them (checked with v441, the same as
  with v425); Nil Python refuses hosted riscv32 Linux in v441 with a message
  that says so and points to the ESP32 build instead. From v450 it builds
  and runs there (see "Since v441").
- **wasm32** runs under wasmtime 48.0.1. It is the least tested cross target:
  its suites are run by hand, not continuously.
- **ESP32-S3 (Xtensa)**: real hardware. On one physical ESP32-S3 board
  (ESP-IDF v6.0.1), with this release, all 14 examples and short-form programs
  of the earlier board walk passed, as did `spi-s3`, `monitor-s3`, the Nil
  Python Wi-Fi station page and the socket-error test. These include
  GPIO-edge and ADC programs that QEMU cannot exercise and seven Nil Python
  programs. The peripheral units (GPIO, UART, ADC, PWM, I2C, SPI,
  stored settings, timers) are usable from Pascal and from Nil Python; I2C and
  SPI have been checked on the bus without a device attached, never against a
  real device.
- **ESP32-C3 (RISC-V)**: real hardware and QEMU. The C3 examples ran on
  one physical C3 board with pin v441, all passing, with 0-byte heap soaks
  and a Wi-Fi join (docs/examples/index.md, "On a real ESP32-C3").
- This release has **no Windows, macOS or BSD target**.

## Demos

- **The examples showcase** (`docs/examples/index.md`): terminal and GTK
  Pascal applications, Eliah, an IDE written in PXX, a chess engine, parallel
  programs, Nil Python programs, ESP32 programs, and a bootable minimal Linux
  system whose shell and compiler were built by PXX.
- **Real C programs, compiled unmodified** and checked against GCC's build of
  the same source or against their recorded expected output (re-checked with
  v441 and again with v450; every row as with v425): SQLite 3.46.0, Lua 5.4.7, zlib 1.3.1, cJSON 1.7.18,
  Duktape 2.7.0, QuickJS (quickjs-ng 0.9.0), the Tiny C Compiler,
  tiny-regex-c, ENet 1.3.18 and BusyBox 1.36.1.
- **BusyBox with no libc.** BusyBox with its applets (`cat` and `echo`) in
  one source file compiles to a **171,224-byte static executable**
  (measured with v441 and v450; the same size as with v425)
  with no dynamic section, no interpreter and no libc, and its output is
  byte-identical to a GCC build over 29 cases. A second route, 55 objects
  linked by PXX's own linker with no external `ld`, is byte-identical to GCC
  over 82 cases.
- **lekkerzeilen**, a separate project: a 3D sailing simulator on the real
  Dutch rivers, written in ordinary Python with SDL2 and OpenGL. **The same
  source compiles with PXX into one native binary, with sound, and runs**,
  about 20 times slower than CPython 3.14.4 in the one scene measured (the
  start scene: 1.89 against 37.1 frames per second). That was measured with
  pin v416, not with this release; other scenes behave very differently.

## Known limits

- **BusyBox and the other C libraries are not included.** Their sources are
  fetched by you: `tools/install_lib_candidates.sh busybox` (and likewise
  `sqlite`, `lua`, `zlib`, …) fetches the pinned upstream commit into
  `library_candidates/`, which is not part of the release archive.
- **Memory leaks were treated as release blockers, and none caused by the
  compiler is known in this release.** A pre-release sweep re-ran all 164
  automated leak checks, 49 Pascal shapes on seven targets at `-O0` to `-O3`,
  threaded programs on four targets, and real programs (uforth, the Pascal
  examples, Lua 5.4); the Nil Python checks ran beside a deliberate leak
  they had to catch (the Pascal checks got one later, see above). It found
  five compiler-caused leaks, all fixed in this release: `Dispose` did not
  finalize its pointee, `Finalize` of a fixed array released only the first
  element, `Dispose(F())` of a call result, and in Nil Python a rebound `for`
  target and a `lambda` passed as an argument. ESP networking under QEMU
  (10,000 HTTP requests, MQTT, NTP and a Pascal TCP loop) showed no growth.
  Real Wi-Fi was soaked afterwards on both boards (see the Highlights: 0
  errors, free heap higher at the end). On the ESP32-C3, long network runs
  stall under QEMU in the emulated network card; that is not a leak. Details:
  `docs/reference/known-issues.md`.
- **One riscv32 row is unresolved.** `wait4()` leaves its `rusage` argument
  untouched on riscv32 in one test, but only ever under QEMU 8.2.2 on one
  test host; it does not reproduce under QEMU 10.2.1. Whether that is a PXX
  defect or an emulator gap has not been separated.
- **ESP bare-metal images run under QEMU only.** On a real ESP32-S3 a bare
  image faults on its first byte-sized memory access; use the ESP-IDF profile
  on hardware.
- **A few programs compile and silently give a wrong answer.** C `long double`
  is 8 bytes, not GCC's 16, and an initialised C `__thread` variable reads 0
  outside the main thread. The full list is `docs/reference/known-issues.md`.
- `-O2` is the default and the level the compiler proves on itself. `-O3` is
  experimental.
- Integer division by zero gives 0 on ESP and stops the program on desktop.
  That is by design: an embedded device keeps running.

What changed in the compiler and its libraries between pin v441 and this
release.

**Memory leaks**

- Nil Python: a list or dict that a statement creates (`kept = []`) is freed
  when its last name lets go of it; before, it stayed allocated until the same
  statement ran again or the function returned. `31d314dfa8` (v446)
- Nil Python: a list built by a comprehension is freed the same way when its
  name lets go (`rows = [...]; rows = None`); before, it was held until the
  function returned. `cdd6fd3c1f` (v447)
- Nil Python: calling a Pascal routine that returns either `Self` or a new
  object (`if v > 0 then Exit(Self); Result := TA.Create`) no longer keeps
  every new object: 500 of 500 stayed allocated with v443. Measured again
  on 2026-09-28, 500 such calls inside a function: 500 objects alive after
  it returned with pin v447, 0 with pin v448 on x86-64, i386 and arm32.
  `180411ab1e` (v448)
- wasm32: a function returning a record with managed fields, string literals,
  and a `const` argument that is indexed no longer leak on every loop trip.
  Two tests that grew with their trip count on wasm32 only (393 to 1,797 and
  488 to 1,925 live at four times the trips, with v446) stay at 8 and 6.
  `4b14336cc2` (v447)
- Nil Python: a computed string on the left of `*` (`str(i) * 2`,
  `"%d" % i * 2`, `s.upper() * 2`) no longer leaks one string per evaluation.
  `c64b304036` (v446)
- Pascal and Nil Python: a Pascal function whose result is a field, an array
  element or a global no longer has that object freed under its holder. In
  Nil Python, calling `re.compile` twice in a function answered wrongly the
  second time (a use-after-free). `601abeecec` (v446)
- Nil Python: `list.clear()` and `dict.clear()` release the elements they
  drop; before, 20 cleared strings stayed allocated per call. `fbfdcd1ea8` (v442)
- Pascal: a handled exception runs its destructor once, as in FPC; before,
  its memory was released and its `Destroy` never ran. An exception class
  owning a `TStringList` lost it on every raise: 500 raises left 1,892 blocks
  live with v448 and 4 after the fix. `846a574b00` (v449)
- Nil Python: `del name` releases what the name refers to; from v446 to v448
  it stayed allocated until the function returned. A list of 30 strings left
  32 live under `del` with v448 and 1 after the fix. `c4f5dcf929` (v449)

**Silent wrong values (C)**

- A struct member typed by an array typedef (`typedef int arr3[3]`, cglm's
  `mat4`) is laid out at its full size; before, it took one element's space and
  writing to it overwrote the next member. `f713506115` (v444)
- An array of pointers to arrays (`mat4 *m[3]`) has the right size, and each
  element knows what it points at; before, `sizeof m` was 192 (GCC 24) and
  `*m[i]` read the wrong memory. `c5ad9480c4` (v443)
- `sizeof(*(p))` for a pointer to an array gives the array's size, not a
  pointer's. `84b57aa495` (v445)
- `&x + 1` steps by the size of `x`; before, it stepped one byte for every
  operand. An array typedef of structs is laid out as an array. `47f3bbccd4`
  (v446)
- A function returning a pointer to an array (`vec4 *f(void)`) gives a
  pointer to the whole array: `sizeof *f()`, `f() + 1` and `(*f())[i]` match
  GCC. `52759b8a2e` (v446)
- Five values that were right only on x86-64, among them `size_t`
  arithmetic, now match GCC on i386, aarch64, arm32 and riscv32.
  `be48b8d2e3` (v446)
- An initialised `__thread` variable starts at its initialiser in every
  thread, not only in the main one. `ce34aa72ef` (v446)

**Silent wrong values (Pascal, 32-bit and cross targets)**

- Six values that differed by target, among them a cast of untyped memory
  (`Int64(p^)`) read at the wrong width. `ba448efdb8` (v447)
- `c.L^[i]` on a property getter's result reads the right element.
  `516028aa3e` (v447)
- riscv32: assigning to a `var s: string[N]` parameter reaches the caller.
  `3b31d3d6b7` (v447)
- arm32: a Pascal callback called from C (`qsort`'s comparator) keeps the
  registers the ARM ABI says it must preserve; sorting 3 or more elements
  crashed. `79d1deb549` (v447)
- A string element passed to a `var` parameter, `Move` or `FillChar` makes
  the string unique first, as in FPC. `SetC(s[2])` on a literal crashed on
  x86-64, i386, arm32 and aarch64 with v448, and on riscv32 it changed a
  string that shared the buffer. `cbbb1e6418` (v449)

**Threads**

- i386 gives every thread its own `__thread` block, and Pascal `threadvar`
  compiles there. `7dc976a8cc` (v446)
- Threads created by PXX on i386, aarch64 and arm32 no longer share glibc's
  thread pointer, which made a threaded program that uses libc's `malloc`
  abort in some runs. `0ed2b7f6e1` (v446)

**Helpers**

- A `record helper for` a user record type is found on the record.
  `cc9ea7228a` (v447)
- A bare helper member inside `with x do` is found. `50329e2988` (v447)

**ESP32**

- ESP32-S3: a Nil Python program that uses `re` compiles; with v447 every
  one stopped with "aggregate-result frame offset out of range". Measured on
  2026-09-28 by building such a program for the S3 with pins v447 and v448.
  On a physical S3 with the v448 binary, the `re` operations printed
  CPython's answers and a 2,000-iteration soak stayed flat (recorded in
  `devdocs/progress/LOGBOOK.md` by commit 19f4728e10). `1c2fb47dd8` (v448)
- `import ssl` works on the ESP32: `urequests.get("https://...")` and
  `umqtt.simple` with `ssl=True` run unchanged, with certificate checking on
  request. `97af9cde4f` (v442)

**Nil Python**

- `re.findall` returns every match; it stopped at 4096 without saying so.
  `re` also no longer asks for about 800 KB per call: one `re.compile` and a
  `findall` allocated 820,384 bytes with pin v447 and 5,432 with pin v448 on
  x86-64, and on an ESP32-C3 under QEMU v447 ran out of memory and rebooted
  in a loop where v448 prints its results. The 4096 limit was measured on
  x86-64 with v447, and gone with v448 on x86-64, i386, aarch64 and arm32.
  `2c3302f96e` (v448)
- `m.start()` and `m.end()` with no argument mean group 0, as in CPython;
  they did not compile. `19f4728e10` (v449)
- A float captured by a lambda, or by a nested def taken as a value, keeps
  its value: `bare(1.0)` gave `0.0` on i386 and arm32 with v448. Measured
  under QEMU user mode, Xtensa included; on ESP32-C3 and ESP32-S3 boards it
  was reported, in a report not yet recorded in the repository. `dbd60352fd` (v449)
- On arm32 a float default no longer stops the program with SIGBUS; with
  v448 it did, once the layout shifted. `4a9cf4c07c` (v449)
- On the ESP32-S3, `cls = P; cls(x)` inside a def or method passes its
  arguments; with v448 the object's fields read `0`. Measured on Xtensa
  under QEMU user mode; on S3 and C3 boards it was reported, in a report not
  yet recorded in the repository.
  `76d35e065f` (v449)
- Eleven places where Nil Python on i386, aarch64 or arm32 differed from
  x86-64 and CPython, found by building the test corpus for each: among
  them, a generator called with a string literal segfaulted (on every
  target), a float converted to `int` stopped at 2^31 on arm32, and 32-bit
  generators, `%x` of a large number, and `round` of an int went wrong.
  Measured on 2026-09-28: a generator over `"abc"` segfaulted with pin v447
  on x86-64, and gave `[]` on i386; `int(3000000000.5)` gave 2147483647 on
  arm32. With pin v448 all three give CPython's answers on x86-64, i386 and
  arm32. `679dc870b5` (v448)
- A class body's attribute initialisers can read the class attributes defined
  above them, as in CPython (the `ina219` driver's constant table).
  `cdb8162bfd` (v444)
- String methods and indexing on a member or a call result
  (`r.text.split(":")[0]`, `R().name.upper()`) give Python's answer; before,
  some were refused, one raised a `TypeError` and one indexed from 1. Of 240
  such shapes compared with CPython, 73 were wrong with v443 and none are now.

## Fixed since the draft pin v425

- On ESP, an uncaught exception prints its message. What follows is pending a
  decision: currently the main task spins, and on the ESP32-C3 under QEMU the
  watchdog then reboots the chip.
- C member access and subscripts on a pointer out of a comma, `?:` or `=`
  expression read the right field.
- C compound literals of an array type are accepted in every shape, including
  through array typedefs such as cglm's `mat4`.
- A designator with a function call in it, such as `a[Pick(i)].Free`, calls
  the function once.
- A recursive `pthread` mutex can be re-locked (SQLite with threads no longer
  hangs).
- The five memory leaks listed above.

wasm32 needs wasmtime, and the ESP32 needs ESP-IDF v6.0.1
(`docs/getting-started/esp32.md`); `./pxx --doctor` says whether QEMU and
ESP-IDF are found. Unpack the archive, then:

```sh
./install.sh --yes    # writes ./pxx: this host's prebuilt compiler + the library roots
./pxx examples/primes/sieve.pas /tmp/sieve && /tmp/sieve
./selfcheck.sh        # optional: rebuild every shipped binary, diff against MANIFEST.sha256
```

`RELEASE.md` in the archive describes its layout and how to rebuild
everything from the included source.

## Reporting bugs

Open an issue at <https://github.com/yoctobyte/pxx/issues> with the smallest
source file that shows the problem, the exact command you ran, what you
expected (GCC's output for C, FPC's for Pascal, CPython's for Nil Python) and
what you got, the output of `./pxx --doctor`, and the compiler `./pxx` ran:
`sha256sum "$(./pxx --where | sed -n 's/^binary: *//p')"`. `docs/reference/reporting-bugs.md`
(on the site: Reference, Reporting bugs) says what else to include and how to
make a small reproducer. **Programs that compile and quietly give a wrong
answer are the most valuable reports.**
