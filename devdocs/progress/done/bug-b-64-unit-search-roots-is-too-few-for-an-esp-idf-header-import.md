# 64 unit search roots is too few for an ESP-IDF header import

- **Type:** bug / limit (driver, unit search) — **Track A**.
- **Filed:** 2026-10-05 from `~/museum_landkaart` (an ESP32-C3 app on ESP-IDF
  v6.0.1). The app declares every IDF routine as a hand-written `external` and
  fills IDF structs at generated byte offsets. The user wants it to `uses` the
  IDF headers directly instead, which the cross-language docs say should work
  (`uses gtk3_c;` → a `.h`).

## Repro

```sh
# include flags of any IDF TU, from esp/build/compile_commands.json
#   (81 -I, plus -DESP_PLATFORM etc.)
cat > hdrtest.pas <<'EOF'
program hdrtest;
uses esp_wifi;
begin
end.
EOF
pxx --target=riscv32 --platform=esp --no-signals --emit-obj \
  -Fu$PXX/lib/rtl -Fu$PXX/lib/rtl/platform/esp $IDF_FLAGS hdrtest.pas hdrtest.o
# pascal26:0: error: too many -Fu/-I unit directories
```

## Boundary

- Only the limit has been measured. Whether pxx's preprocessor and C frontend
  then get through `esp_wifi.h` and its includes (FreeRTOS, newlib `sys/`,
  GCC's own `include/`, sdkconfig.h) is **unknown**: the experiment stopped at
  this error.
- Workaround, not tried yet: `esp_wifi.h` + `esp_netif.h` + `esp_event.h` +
  `nvs_flash.h` + `esp_sntp.h` + `driver/rmt_tx.h` together touch only 33 of
  the 81 IDF dirs (found with `riscv32-esp-elf-gcc -H`), plus 4 toolchain dirs.
- Function-like initialiser macros such as `WIFI_INIT_CONFIG_DEFAULT()` would
  still need a Pascal equivalent even once the header imports. That is the next
  question after this ticket, and a separate one.

## Acceptance

A real IDF include set (≥ 100 roots, for headroom) is accepted, or the limit
goes away (a dynamic list). Then the next error, if any, is filed against the
header parse itself.

## Log

- 2026-10-05: filed from museum_landkaart. The app keeps its hand-written
  externals until header import is proven on-target (user: "be safe and let me
  have proven working code").

## Resolution (2026-11-01)

Fixed already, in e30cf0f1df: MAX_PAS_UNIT_DIRS is 256 (compiler/defs.inc:422, with
a comment naming the IDF TU's 81 -I). This ticket was never committed, so nothing
tracked it. The header-parse follow-up it asked for was explored separately
(museum_landkaart async/tools/idf_census.sh). The app still uses hand-written
externals, by the user's choice.
